GPU-Passthrough Virtualization Lab

KVM/QEMUVFIOIOMMULinuxisolation

Overview

I built a Linux host running KVM/QEMU that passes my GPU straight through to a Windows VM for near-native performance — but with a twist most passthrough setups don't do: it's a single-GPU, dynamically bound rig. There's only one 4090 in the machine, and rather than isolating it at boot (which would leave the host without a GPU), I bind and unbind it on demand. The card lives on the host for my X session and local-LLM work, and gets handed to the VM only when I want it — then handed back cleanly afterwards.

What it involved

  • IOMMU & VFIO: enabled IOMMU, inspected IOMMU groups, and drive the vfio-pci binding at runtime rather than at boot, so the host keeps the GPU until I explicitly release it.
  • Guest configuration: configured the QEMU/libvirt domain with the passed-through GPU, CPU pinning, and hugepages for stable performance.
  • Isolation goals: a snapshot-based, network-segmented guest I can revert — a safe place to detonate samples and run RE tooling without touching the host.
  • Troubleshooting: worked through the usual passthrough pain — group splitting, vendor-reset quirks, and getting the host to hand off the device.

Dynamic single-GPU passthrough

The interesting part is the handoff. With one GPU, the workflow is: do my normal host work (X session, local LLM inference) on the 4090; when I want the VM, I log out of the X session, run the script below, and it tears the GPU off the host, binds it to vfio-pci, and boots the VM with the card. When I shut the VM down, the driver is gracefully reattached to the host and it's ready to serve my X session or LLM work again — no reboot, no second GPU.

An orchestration script ties it together: it frees the GPU host-side (including stopping the llama-server from my offline-LLM project), binds to VFIO via a root helper, starts the VM, waits for it to power off, then unbinds and returns the card to the host:

#!/bin/bash
VM_NAME="win10"
export LIBVIRT_DEFAULT_URI=qemu:///system
export XDG_RUNTIME_DIR=/run/user/1000
export PULSE_SERVER=/run/user/1000/pulse/native

# Check VM exists
if ! virsh dominfo $VM_NAME &>/dev/null; then
    echo "ERROR: VM '$VM_NAME' not found"; exit 1
fi

# Load vfio module if needed
if ! lsmod | grep -q vfio_pci; then
    sudo modprobe vfio-pci
fi

# Free the GPU on the host side (stop local LLM server)
killall llama-server 2>/dev/null
sleep 2

# Bind GPU to vfio (root via sudoers)
echo "Binding 4090 to vfio..."
sudo /usr/local/bin/vfio-bind.sh bind

# Start VM as regular user (keeps PulseAudio access)
echo "Starting VM..."
virsh start $VM_NAME || { sudo /usr/local/bin/vfio-bind.sh unbind; exit 1; }

echo "VM running — waiting for shutdown..."
while true; do
    STATE=$(virsh domstate $VM_NAME 2>/dev/null)
    [ "$STATE" = "shut off" ] || [ "$STATE" = "crashed" ] && break
    sleep 5
done

# Graceful return to host
echo "VM stopped"
sudo /usr/local/bin/vfio-bind.sh unbind
echo "Done — 4090 returned to host"

A few details that made it robust: the GPU release is wrapped so a failed VM start still unbinds and restores the host; the bind/unbind helper runs as root through a tight sudoers rule while the VM itself starts as the regular user to keep PulseAudio audio; and the script blocks on VM state so the card is only reclaimed once the guest has fully powered off.

How it maps to security work

Isolated, revertible VMs are the backbone of any malware analysis or detonation lab, and the underlying concepts — device isolation, IOMMU, runtime driver/device rebinding, hypervisor configuration, network segmentation — are core to understanding both virtualization security and how analysts safely study hostile code. The single-GPU dynamic handoff in particular is a real exercise in Linux internals, kernel driver binding, and least-privilege automation (root only for the bind step, via a scoped sudoers rule).

Note. Built and run entirely on hardware I own, as a personal lab environment for learning systems and security tooling.

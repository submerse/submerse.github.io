Overview

This started as a question: what exactly is anti-cheat software doing? That question doesn't have a clean answer from the outside. To understand a defender, you have to understand the attack surface it's defending — and the only way to genuinely understand that surface is to build something that works against it. This tool is the result of that exercise.

Over six iterations it grew from a basic memory reader into a multi-featured tool: a transparent fullscreen ESP overlay drawing entity boxes, health bars, and bone-accurate head circles; an aimbot with Bezier-smoothed angle writes and runtime recoil correction; a triggerbot that monitors a game-internal pointer chain for crosshair contact; and a radar hack that forces enemies visible on the minimap. All running concurrently across seven background threads, configured through a tabbed GUI.

The point was never the features. The point was the mental model they force you to build: a running process is not a black box. Its internal state is fully readable by anything with the right handle, its behaviour fully modifiable by anything with write access, and the only thing standing between an attacker and that access is the OS permission model and the software in the same privilege ring enforcing it. Building something that breaks a game is one of the fastest ways to understand what defending a process actually requires.

Part 1 — The Starting Point: What Is Process Memory?

Before writing a line of code, the first problem is conceptual. How does a running Windows process store its game state, and how does any external program reach it?

Windows gives every process its own virtual address space — 4 GB for a 32-bit process like CS:GO. The game engine allocates objects on the heap at runtime: players, weapons, world geometry. Those objects live at addresses that shift between sessions due to ASLR, but large modules like client.dll load at consistent base addresses that can be queried through the Windows API. Every value visible on screen — player positions, health, view angles — exists in that address space as raw bytes.

ReadProcessMemory and WriteProcessMemory are the Windows API calls that let a process with PROCESS_VM_READ access reach into another process's address space. pymem wraps them in Python, handles process attachment via OpenProcess, and provides typed read methods (read_float, read_int, read_uint) that translate raw bytes into usable values. Attaching to the target and querying the module base is the first checkpoint:

initial attachment 
pm = pymem.Pymem("csgo.exe")
client = pymem.process.module_from_name(pm.process_handle, "client.dll").lpBaseOfDll

If those two lines run without a PermissionError, you're in. The moment you print a float from the process's memory and recognise it as a plausible world coordinate, something becomes concrete about how exposed a running process's internal state is to anything holding the right handle.

The immediate next thought — and this is the security research framing kicking in — is that this is exactly what a debugger does. What a memory forensics tool does against a running malware sample. What a vulnerability researcher does when they attach to a target binary. The tool is different; the primitive is identical. Starting with a game just makes the feedback loop fast: you can see immediately whether your read makes sense.

Part 2 — Finding the Data: Offset Research

The hardest part of this project was not the code. It was offset research — finding the fixed distances from a known stable address (client.dll's base) to the specific fields inside game objects. The entity list lives at client.dll + 0x04E2520C. An entity's health is at entity_ptr + 0xF8. Position X is at entity_ptr + 0x130. None of these are documented anywhere. Finding them is a reverse engineering problem.

Cheat Engine as a Dynamic Analysis Tool

Cheat Engine is the tool for this. It's a memory scanner and debugger aimed at games, but its core functionality — value search, narrowing, pointer tracing — is the same category of dynamic analysis as a PIN instrumenter or a Frida hook.

The methodology: attach to the running game, search for a known value (your current health: 100). Take damage. Search for the new value (85). The candidate address list drops from millions to a handful. Repeat until one address remains. You've located the health field in the live heap.

The problem: raw heap addresses change every session. The goal is an offset from a stable base — client.dll, which loads at a reproducible address. Cheat Engine can trace pointer chains back from a dynamic address to a module base, exposing the chain of pointer dereferences the engine itself uses to reach that field. This is how the NAME_BASE_PTR_OFFSET and NAME_CHAIN constants in the code were found:

pointer chain — resolved in code 
NAME_BASE_PTR_OFFSET = 0x0534D810
NAME_CHAIN           = [0x17C, 0xA0, 0x18, 0x34, 0x310]

entity_list_2 = resolve_pointer_chain(pm, client + NAME_BASE_PTR_OFFSET, NAME_CHAIN)

Walking that chain manually in Cheat Engine before translating it to code reveals the structure of the engine's internal object graph — which pointer leads to which container, at what stride the entity array is indexed. This is identical to the methodology used when reverse engineering any binary that manages structured heap data: trace from a known stable reference, follow pointers, identify strides and offsets.

resolve_pointer_chain — step by step 
def resolve_pointer_chain(pm, base, chain):
    addr = pm.read_uint(base)            # (1) dereference the root pointer
    for offset in chain[:-1]:           # (2) walk every level except the last
        addr = pm.read_uint(addr + offset)
    return addr + chain[-1]             # (3) final offset added, NOT dereferenced
step 1 — root dereference

pm.read_uint(base) reads 4 bytes at base and interprets them as an unsigned integer — an address. This is a pointer dereference: you're not reading a value, you're reading where to look next. The result is a heap address somewhere in the game's address space.

step 2 — chain traversal

For each offset in the chain except the last: add the offset to the current address and dereference again. Each iteration lands in a different object — a container, a manager class, a sub-struct. The offset is the field position within that object where the next pointer lives. This mirrors exactly what the game's own compiled code does when it walks its internal data structures.

step 3 — final offset, no dereference

The last entry in the chain is added but not dereferenced. It's the byte offset of the target field within the final object — the address you pass to read_float or write_int. Dereferencing it would read the value, which isn't what this function returns; it returns the address so the caller decides how to read it.

why this matters for security research

Walking a pointer chain in live process memory is structurally identical to traversing an object graph in a heap exploit: you follow pointers through allocations to reach a target field, and the offsets you use are derived from the binary's internal layout. The same reasoning applies in IDA when tracing how a global handle leads through a manager class to a vtable entry.

The Patience Problem

Offsets break on game updates. A patch shifts the entity list layout and suddenly health reads return garbage — usually -1 or a suspiciously round number that doesn't match anything real. The only response is going back to Cheat Engine, re-scanning, re-tracing the pointer chain, and updating the constants. Across six versions of the tool this happened multiple times.

That cycle — locate, verify, break, re-locate — is exactly the cycle a malware analyst faces when a sample updates its internal structure to evade a signature. The patience required is the same. You can't shortcut it.

Part 3 — The Overlay: A Transparent Fullscreen Window

Drawing on top of the game requires a surface that is: fullscreen, always on top, visually transparent, and non-interactive (mouse clicks must fall through to the game). Tkinter provides the drawing surface; two Win32 extended window style flags handle the rest.

overlay setup — transparent, click-through 
root.attributes("-topmost", True)
root.attributes("-transparentcolor", "black")
root.overrideredirect(True)   # removes title bar and window chrome
root.geometry(f"{sw}x{sh}+0+0")

canvas = tk.Canvas(root, width=sw, height=sh, bg="black", highlightthickness=0)

hwnd = ctypes.windll.user32.FindWindowW(None, root.title())
make_window_clickthrough(hwnd)
win32 click-through via ctypes 
GWL_EXSTYLE       = -20
WS_EX_LAYERED     = 0x80000
WS_EX_TRANSPARENT = 0x20
LWA_COLORKEY      = 0x1

styles = ctypes.windll.user32.GetWindowLongW(hwnd, GWL_EXSTYLE)
styles |= WS_EX_LAYERED | WS_EX_TRANSPARENT
ctypes.windll.user32.SetWindowLongW(hwnd, GWL_EXSTYLE, styles)
ctypes.windll.user32.SetLayeredWindowAttributes(hwnd, 0x000000, 0, LWA_COLORKEY)

WS_EX_LAYERED enables color-key transparency — anything drawn in pure black becomes invisible. WS_EX_TRANSPARENT makes the window non-interactive: the OS routes mouse and keyboard events to whichever window is below it in the Z-order, which is the game. The canvas clears and redraws every ~30ms.

The first problem here was timing. Tkinter's HWND doesn't exist until after the first layout pass completes. Calling FindWindowW immediately after root.geometry() returns NULL — the window isn't registered yet. root.update_idletasks() forces the layout pass before the Win32 call. Without it, FindWindowW returns NULL silently, the click-through setup never runs, and the overlay blocks all mouse input to the game. A silent failure that took a while to diagnose because nothing visibly breaks until you try to click something in-game.

Part 4 — ESP: Projecting the World onto the Screen

ESP (Extra Sensory Perception) draws boxes, health bars, and labels around entities. The central problem: entity positions exist in 3D world space; the overlay is 2D screen space. The game's view matrix bridges them.

World-to-Screen Projection

The view matrix is a 4×4 float matrix at client.dll + 0x4DF85A4. It encodes the camera's orientation and projection transform. Multiplying a 3D world coordinate through it produces a clip-space coordinate that normalises to a pixel position:

world_to_screen — clip-space projection 
def world_to_screen(pos, matrix, sw, sh):
    x, y, z = pos
    clip_x = x*matrix[0]  + y*matrix[1]  + z*matrix[2]  + matrix[3]
    clip_y = x*matrix[4]  + y*matrix[5]  + z*matrix[6]  + matrix[7]
    clip_w = x*matrix[12] + y*matrix[13] + z*matrix[14] + matrix[15]
    if clip_w < 0.01:
        return None          # entity is behind the camera
    ndc_x = clip_x / clip_w
    ndc_y = clip_y / clip_w
    return int(sw/2 + ndc_x*sw/2), int(sh/2 - ndc_y*sh/2)
step 1 — matrix multiply into clip space

The view matrix is 16 floats laid out row-major. Multiplying the world position (x, y, z, 1) through it produces three clip-space components. clip_x and clip_y use rows 0 and 1 of the matrix. clip_w uses row 3 (indices 12–15) — the perspective row that encodes depth. The implicit fourth input component is 1, which is why the matrix[3], matrix[7], and matrix[15] translation terms are added directly.

step 2 — the w component and perspective divide

clip_w encodes how far the point is from the camera along the view axis. Dividing clip_x and clip_y by it is the perspective divide — it shrinks coordinates for distant points (large w) and expands them for close ones (small w), producing the natural foreshortening effect. After the divide, ndc_x and ndc_y live in the range [−1, 1]: NDC (Normalized Device Coordinates).

step 3 — ndc to pixel

ndc_x = −1 is the left screen edge, +1 is the right. Mapping to pixels: sw/2 + ndc_x * sw/2. For Y the sign flips — NDC Y increases upward but screen Y increases downward, so the formula is sh/2 − ndc_y * sh/2. A point dead centre of the camera (ndc 0, 0) maps to the screen centre.

step 4 — the clip_w guard

If clip_w is negative the point is behind the camera's near clip plane. Dividing by a negative number inverts the sign of both NDC values, mirroring the projected position to the opposite side of the screen. Early versions drew boxes in the wrong screen quadrant for entities directly behind the player — the guard short-circuits that case entirely by returning None.

Entity Loop and Box Drawing

The entity list holds up to 64 entries. For each slot: read the entity pointer, skip empty or invalid pointers, skip dead entities (health ≤ 0) and local player, project foot and head positions, derive the box from the head-to-foot pixel distance:

entity loop — box construction 
feet_screen = world_to_screen((ex, ey, ez),     view_matrix, sw, sh)
head_screen = world_to_screen((ex, ey, head_z), view_matrix, sw, sh)

box_h = fy - hy            # pixel height foot-to-head
box_w = box_h // 2         # proportional width
x1, y1 = fx - box_w//2, hy
x2, y2 = fx + box_w//2, fy

canvas.create_rectangle(x1, y1, x2, y2, outline=box_color, width=2)

The proportional width (half the height) keeps boxes plausible at all distances — a player far away gets a thin narrow box, close up a wider one. The head Z calculation factors in crouch state via a delta interpolated from a crouch float offset:

delta  = max(0.0, min(1.0, (72.0 - crouch) / 18.0))
head_z = ez + 70 - (HEAD_OFFSET * delta)

Without the crouch factor, crouched players show a box that overshoots the head — the foot position is correct but the head calculation assumes standing height. The delta smoothly interpolates between standing and crouched head height as the crouch float transitions.

Bone Matrix and Head Circle

The flat box felt imprecise for the aimbot's benefit. The game stores a bone matrix for each entity at entity_ptr + 0x26A0 — an array of 4×3 float matrices, one per bone. Reading the highest-Z bone among IDs 6, 8, and 12 (neck/head area) gives an exact world-space head position:

bone matrix — head position extraction 
bm_ptr = pm.read_uint(ent_ptr + 0x26A0)
best_bone  = None
highest_bz = -float("inf")
for bone_id in [6, 8, 12]:
    off  = bone_id * 0x30
    bx_  = pm.read_float(bm_ptr + off + 0x0C)
    by_  = pm.read_float(bm_ptr + off + 0x1C)
    bz_  = pm.read_float(bm_ptr + off + 0x2C)
    if bz_ > highest_bz:
        highest_bz = bz_
        best_bone  = (bx_, by_, bz_)

Projecting the head bone and a virtual point 7 units above it gives a pixel radius that scales naturally with distance. The circle is drawn on top of the box and served as the aimbot's visual confirmation that the bone target was being resolved correctly before angle writes were added.

Flicker and the Tkinter Thread Problem

Early versions flickered badly. The cause: calling canvas.create_rectangle() directly from a background thread. Tkinter's internal state is not thread-safe — concurrent access from the ESP thread and the main Tkinter event loop produced intermittent corruption and visual tearing. The fix was keeping all canvas operations inside the ESP thread but ensuring it ran on the main thread's after() scheduler. Alternatively, running the ESP loop itself as the main thread content (which is what the final architecture does) and using time.sleep(0.03) as the frame gate.

Part 5 — Aimbot: Writing Angles

Reading game state is one kind of access. Writing to it is another. The aimbot reads the current view angles, computes where they need to point, and writes the corrected values back into the game's memory — overriding what the mouse produced. This is WriteProcessMemory used offensively.

Angle Math

The view angles live behind a two-level pointer rooted in stdshader_dx9.dll — a non-obvious location that took CE pointer scanning to find. Pitch (vertical) and yaw (horizontal) are stored as floats. Computing the required angle to a target is straightforward trigonometry:

angle calculation — atan2 pitch/yaw 
def calc_angle(src, dst):
    dx, dy, dz = dst[0]-src[0], dst[1]-src[1], dst[2]-src[2]
    hyp = math.sqrt(dx*dx + dy*dy)
    return -math.degrees(math.atan2(dz, hyp)), math.degrees(math.atan2(dy, dx))

Pitch is negated because CS:GO's coordinate system has positive pitch pointing downward (looking up requires a negative value). Yaw wrapping is the subtle problem: angles live in (-180, 180] and when a target crosses the ±180 boundary, naive subtraction gives a ~360° jump instead of a small step. The angle_diff function normalises it:

def angle_diff(a1, a2):
    dp = a1[0] - a2[0]
    dy = ((a1[1]-a2[1])+180) % 360 - 180
    return math.sqrt(dp*dp + dy*dy)
calc_angle — what atan2 is doing

dx, dy, dz is the raw displacement vector from the local player's feet to the target bone. hyp is the horizontal ground distance — the length of the vector projected onto the XY plane, ignoring height. atan2(dz, hyp) gives the vertical angle above or below the horizontal — if the target is above you, dz is positive and atan2 returns a positive angle. CS:GO's pitch convention is inverted (positive pitch = looking down), so the result is negated. atan2(dy, dx) gives the compass bearing on the XY plane — yaw, ranging from −180° to +180°.

angle_diff — the yaw wrap problem

Imagine the local player is facing 179° and the target is at −179°. The real angular gap is 2°. But naive subtraction gives 179 − (−179) = 358° — the long way around the circle. This makes the target appear to be 358° outside the FOV cone, so it's never selected as a valid aim target. The formula ((a1−a2) + 180) % 360 − 180 fixes it: adding 180 shifts the result into [0°, 360°), modulo 360 wraps it, subtracting 180 maps it back to [−180°, +180°). The result is always the shortest angular distance between two headings regardless of which side of the ±180° boundary they sit on.

Bezier Smoothing

Snapping directly to the target angle is instantly detectable — a zero-latency perfect correction is a statistical impossibility in real mouse input. The aim interpolates along a cubic Bezier curve instead, with a parameter t that increments each frame:

bezier smooth angle — cubic interpolation 
def bezier_smooth_angle(current, target, t):
    p0, y0 = current
    p3, y3 = target
    p1 = p0 + (p3-p0)*0.25    # control point 1 — 25% along
    p2 = p0 + (p3-p0)*0.75    # control point 2 — 75% along
    y1 = y0 + ((y3-y0+180)%360-180)*0.25
    y2 = y0 + ((y3-y0+180)%360-180)*0.75
    return bezier_point(p0,p1,p2,p3,t), bezier_point(y0,y1,y2,y3,t)
step 1 — the cubic bernstein formula

bezier_point evaluates the standard cubic Bézier polynomial: B(t) = (1−t)³·P0 + 3(1−t)²t·P1 + 3(1−t)t²·P2 + t³·P3. u = 1 − t is just the complement of t — shorthand to avoid repeating (1−t) four times. P0 is the start, P3 is the end, and P1/P2 are control points that shape the curve between them.

step 2 — what t does at the extremes

At t = 0: u = 1, so u³·P0 = P0 and every other term has a t factor that collapses to zero — result is exactly P0, the current angle. At t = 1: u = 0, so every term with a u factor collapses — result is exactly P3, the target angle. Between 0 and 1 the four terms blend smoothly, with their weights always summing to 1.

step 3 — control points at 25% and 75%

p1 = p0 + (p3−p0)·0.25 places the first control point a quarter of the way along the direct line from start to target. p2 sits at 75%. With both control points on the straight line between start and end, the curve doesn't deviate sideways — it stays on the direct angular path. But the cubic weighting still produces ease-in/ease-out: the aim accelerates leaving the start and decelerates arriving at the target, because the high-order t³ and u³ terms dominate near the endpoints and change slowly there.

step 4 — yaw wrapping inside bezier_smooth_angle

Yaw can't be interpolated naively. If current yaw is 170° and the target is −170°, a straight lerp sweeps 340° the long way around. The control point offsets use the same shortest-path trick as angle_diff: ((y3−y0+180)%360−180) gives the signed shortest delta, and the control points are placed along that arc rather than across the ±180° boundary.

step 5 — why this fools timing analysis

A raw memory write that snaps the angle to the target in one frame produces a velocity spike — an instantaneous delta of potentially 90°+ in 10ms, which is physically impossible for a human wrist. Anti-cheat systems that log view angle deltas per frame will flag this as a statistical outlier. The Bezier spreads the same total angular movement across many frames with a natural deceleration profile, making the per-frame deltas indistinguishable from fast human mouse input.

The smoothing slider in the config GUI controls how fast t increments per frame — which is the only dial between instant and slow. At the high end, t reaches 1 in a single step: the aim locks onto the head in one frame. At the low end it creeps over many frames, producing a gradual arc that reads as human tracking. The Bezier curve runs in all three cases — even at maximum speed the movement still follows the cubic interpolation path rather than a raw write, keeping the per-frame angle delta within a range that is physically plausible for fast human input.

FOV Cone — Aimbot Activation Radius

The aimbot doesn't lock onto every enemy on the map. It only considers targets whose required aim angle is within a configurable angular distance from the current crosshair — the FOV cone. This is controlled by desired_fov, a degree value set via slider (range 1°–30°):

fov gate — aimbot_thread 
best_fov = shared["desired_fov"]   # start with the threshold as the minimum
...
fov = angle_diff(angle, (cp, cy))  # angular distance: crosshair to enemy
if fov < best_fov:
    best_fov   = fov               # narrowest match wins
    best_angle = angle
    new_target = ent_ptr

angle_diff returns the shortest angular distance between the current view direction and the direction to the enemy head. If that distance is larger than desired_fov, the enemy is outside the cone and the aimbot ignores them entirely — the crosshair must already be pointing roughly at the target for the lock to activate. Among all enemies inside the cone, the one with the smallest angular offset wins.

On the overlay, this cone can be visualised as a circle drawn at the screen centre — a small crosshair-centred ring whose pixel radius corresponds to the degree threshold. A tight FOV (1°–3°) draws a small circle and requires the player to manually aim near the head before the aimbot engages; a wide FOV (15°–30°) draws a large circle and activates across much of the screen. The circle is the same concept as a sniper scope — it defines the zone of engagement rather than doing the aiming itself. Keeping it small is also a deliberate anti-detection measure: a wide FOV that locks onto enemies anywhere on screen is a statistical signature, while a small FOV is indistinguishable from a precise human flick.

Recoil Correction

Writing the correct angle to a stationary target is one problem. Keeping it on a moving crosshair while the gun is firing is another. Automatic weapons produce upward spray — the game's recoil system shifts the view angle upward with each shot, and the aimbot write from the previous frame is immediately overridden by the recoil offset.

The correction is a running pitch offset applied while the left mouse button is held, accumulating over time toward a cap of 54 degrees:

recoil compensation — live pitch offset 
if shared["firing"]:
    if shared["left_hold_start"] is None:
        shared["left_hold_start"] = time.time()
    if time.time() - shared["left_hold_start"] >= 0.05:
        shared["current_pitch_correction"] = min(
            shared["current_pitch_correction"] + shared["correction_speed_2"] * shared["recoil"],
            54.0
        )

Getting correction_speed_2 right required iterative live testing — too fast and the aim overcorrects and dips below the target, too slow and it can't keep up with the spray. F4/F5/F6 hotkeys set recoil presets (40 / 55 / 20) because the right value varies by weapon fire rate and spread pattern.

Part 6 — Triggerbot: Monitoring a Pointer Chain

The triggerbot doesn't detect crosshair contact geometrically. It monitors a specific memory value via a pointer chain and fires the mouse when that value changes. The value encodes something internal to the game's hit detection — when the crosshair crosses an enemy hitbox, a game-internal counter updates.

triggerbot — pointer chain and fire logic 
TB_POINTER_BASE = 0x00DEF97C
TB_OFFSETS      = [0x24, 0x4, 0x68]

ptr   = tb_resolve_pointer(pm, client + TB_POINTER_BASE, TB_OFFSETS)
value = tb_read_value(pm, ptr, "FLOAT")

elif value != prev_value:
    m.press(mouse.Button.left)
    time.sleep(0.05)
    m.release(mouse.Button.left)

This approach is more robust than geometric detection: it uses the game's own hit detection logic rather than external math that might disagree with the server. The tradeoff is brittleness — the pointer chain breaks on game updates and requires re-sourcing from Cheat Engine each time.

The 20ms pre-press delay and 50ms hold are humanisation constants. A zero-latency instant click is a statistical anomaly in real input data. Some anti-cheat systems maintain timing histograms of click events and flag inputs that fall outside the human-achievable minimum latency. Understanding that detection surface is part of what this project teaches — not just how to fire, but what the defender is measuring.

Part 7 — Radar: Writing to Game State

The radar hack is the simplest feature but the most direct demonstration of WriteProcessMemory used offensively. Rather than reading a value and rendering it externally, it modifies the entity's in-game flags directly so the game's own minimap renders enemies as visible:

radar — forcing entity flags via write 
RADAR_FORCE  = {0x0934: 256, 0x0978: 1}
RADAR_TOGGLE = {0x0A20: 1,   0x0A24: 1}

for offset, desired in RADAR_FORCE.items():
    if pm.read_int(ent_ptr + offset) != desired:
        pm.write_int(ent_ptr + offset, desired)

The read-before-write pattern avoids unnecessary writes — only writing when the value has drifted keeps the write volume low, which matters because VAC-style anti-cheats can monitor write frequency to protected memory regions. The flag toggling (RADAR_TOGGLE) alternates each loop iteration to keep a watchdog from detecting a static value that never naturally changes.

This is the same primitive used in process injection: writing controlled bytes into another process's memory to alter its behaviour. The target here is a game flag rather than a shellcode stub, but the Windows API call is identical.

Part 8 — Threading Architecture

Running everything in a single loop would mean the ESP drawing blocks the aimbot, which blocks the triggerbot. Each feature needs its own update rate and must not starve the others. The solution is a thread-per-feature architecture using a shared dict as the message bus:

ThreadIntervalRole
detect_local_player10 sIdentifies local entity index and team
update_entity_info100 msFills entity position cache
esp_loop30 msOwns all canvas drawing (≈33 fps)
aimbot_thread10 msReads angles, writes corrected values
radar_thread50 msWrites entity visibility flags
triggerbot_thread10 msMonitors pointer chain, fires on change
combined_hotkey_listenereventpynput callbacks for all hotkeys

Race conditions exist: multiple threads read and write shared["my_team"], shared["aim_active"], and similar flags without locks. Python's GIL makes individual dict reads and writes atomically safe for simple scalar values, so a stale read here produces at worst a miscoloured box for one frame or a missed trigger event — not a crash. In production code this warrants threading.Lock() around the critical sections. Here it was a conscious tradeoff: adding locks around every shared access would have been noise given the cosmetic-only failure mode.

detect_local_player — Fingerprinting Your Own Entity

The entity list contains every player in the server, including the local player. But the game doesn't store "your entity is at index N" at a fixed, stable offset — the index depends on server connection order and shifts between matches. Every other feature needs to know which entity is you, both to skip drawing a box over yourself and to read your own position as the aimbot's source. The solution is a fingerprinting loop:

detect_local_player — matching by position and health 
base_ptr     = pm.read_uint(client + 0x0526108C)
local_health = pm.read_int(base_ptr + 0x100)
local_x      = pm.read_float(base_ptr + 0x138)
local_z      = pm.read_float(base_ptr + 0x140)

for i in range(MAX_ENTITIES):
    d = math.sqrt((ex - local_x)**2 + (ez - local_z)**2)
    if d < 2.0 and abs(eh - local_health) < 1 and d < closest_dist:
        closest_idx = i
step 1 — read local state from a known pointer

The local player's raw data (position, health) is accessible via a separate stable pointer at client + 0x0526108C — a different path into the engine's local player object that doesn't go through the entity list at all. This gives ground truth values to match against.

step 2 — XZ distance matching

For every entity slot, compute the 2D ground-plane distance between the entity's XZ position and the known local position. Y is omitted because vertical position can differ slightly depending on how the engine interpolates the local player versus the networked entity representation. The 2.0 world-unit threshold accounts for this — it's tight enough to exclude any other player but loose enough for the representation difference.

step 3 — health cross-check

Position alone isn't enough — two entities could briefly share the same position during a spawn. The health cross-check abs(eh − local_health) < 1 adds a second independent dimension. Both conditions must be true simultaneously, making a false positive essentially impossible in practice.

step 4 — 10-second refresh rate

The thread sleeps 10 seconds between scans rather than running every frame. The local entity index is stable within a round — it only changes when the player disconnects and reconnects. Scanning every frame would burn 64 memory reads every 10ms for a value that virtually never changes. The slow refresh is a deliberate read-volume optimisation, the same reasoning behind the radar's read-before-write pattern.

How This Maps to Security Research

Every component of this project has a direct parallel in real security work. The mapping is not metaphorical — it's the same API calls, the same methodology, a different target.

ReadProcessMemory as a Research Primitive

This is exactly what a debugger does when it reads a target process's memory. What a memory forensics tool does when analysing a live malware sample with Volatility or Rekall. What a vulnerability researcher does when they attach to a process under x64dbg and inspect the heap after a controlled allocation. The Windows primitive is ReadProcessMemory in all cases. Building a tool that uses it directly, without the debugger abstraction layer, makes the underlying mechanism concrete in a way that reading documentation does not.

Pointer Chain Traversal

Walking a multi-level pointer chain to locate a target object in a live heap is the same skill used in use-after-free exploitation: understanding object lifetimes, pointer graphs, and what memory looks like after a free. It's the same skill used when reverse engineering a compiled binary in IDA — tracing how a global pointer leads to an object, which leads to a vtable, which leads to a function. Finding NAME_CHAIN = [0x17C, 0xA0, 0x18, 0x34, 0x310] in Cheat Engine required understanding what each dereference landed in. That's the same reasoning process a researcher applies when following a pointer chain in a disassembly listing.

Dynamic Analysis with a Known-Value Scan

The Cheat Engine methodology — known value, change, narrow, repeat — is a specific instance of a broader technique: using known program outputs to locate the internal state that produced them. In exploit research this looks like: allocate a controlled-size buffer, locate it in the heap, establish its offset from a disclosure gadget. In firmware analysis it looks like: send a known command, search the firmware's memory for the response buffer, trace backward to find the processing function. The game just provides the most immediate feedback loop.

WriteProcessMemory and Process Injection

The aimbot writes floats to view angle addresses. The radar writes integers to entity flag fields. The Windows API call for both is WriteProcessMemory. This is structurally identical to the write step in shellcode injection: allocate memory in the target process with VirtualAllocEx, write the payload with WriteProcessMemory, execute it with CreateRemoteThread. Building something that exercises the write primitive makes the mechanism real before approaching the more constrained injection scenarios in security research.

Anti-Cheat as the Defender

The most direct security research connection is the one between this project and the GPU passthrough project. VAC, EAC, and Vanguard are doing the same thing this tool does, from the other direction: scanning for unauthorised ReadProcessMemory calls to game memory, looking for injected modules in the process's module list, monitoring write frequency to protected addresses, checking for memory regions with RWX permissions that don't correspond to any loaded DLL.

Understanding what the attacker can do is prerequisite to understanding what the defender must detect. You cannot reason clearly about anti-cheat evasion (as in the VFIO project) without understanding what anti-cheat is actually measuring. You cannot build a memory protection system without having built something that bypasses naive memory protection. This is the red-team/blue-team knowledge cycle that security research runs on.

The Mental Model It Forces

The most lasting output of this project is not the ESP or the aimbot. It's the internalised understanding that a running process's internal state is not private. Any process with appropriate handle rights can read or modify it. The only enforcement is the OS permission model (token privileges, handle access rights, protected process levels) and the software running in an equal or higher privilege ring to detect abuse. Kernel-mode anti-cheat like Vanguard exists precisely because userspace detection is bypassable with userspace tools — the same tools this project is built with.

That framing — understanding the full permission model and its limits, at the API level — is the prerequisite mental model for Windows internals security research. It doesn't come from reading about it. It comes from building something that demonstrates it.

Current State & What Comes Next

The tool is a research artefact, not a maintained product. CS:GO (now CS2) has shifted to a 64-bit engine and a different memory layout, which broke most offsets. Re-sourcing them for CS2 is a useful future exercise — the methodology is identical but the addresses are different, and 64-bit pointer sizes change the stride calculations.

The natural next step in the same direction is kernel-level work. All of the techniques here operate in userspace, which means they're visible to any kernel-mode monitor. A ReadProcessMemory call from userspace is observable via kernel callbacks (PsSetLoadImageNotifyRoutine, ETW providers, minifilter drivers). Understanding what moves to ring-0 to become undetectable is the same question the GPU passthrough project approaches from the anti-cheat evasion angle — and the same question that leads into driver development, IOCTL analysis, and kernel vulnerability research.

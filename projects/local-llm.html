Self-Hosted Offline LLM Lab

llama.cpp PolyStrata mixture-of-experts quantization GPU offload Pi agent AI red-team Open WebUI WireGuard Caddy fail2ban

Overview

A private language-model lab running entirely on my own hardware, served over my LAN with no third-party API in the path. It started as a 24-billion-parameter model fitted onto a single RTX 4090 through quantization (Part 1). The November 2026 update pushes the same machine to 117–320-billion-parameter mixture-of-experts models by splitting them across VRAM, system RAM and NVMe, and adds a terminal coding agent as the client (Part 2). Part 3 makes the lab reachable from anywhere, with a browser front end, through a WireGuard tunnel and a relay that only ever sees encrypted traffic, without opening a single port at home.

The point is twofold: the systems engineering of efficient local inference, and a controlled environment for studying model behaviour without sending anything to a cloud provider.

Why offline / on-prem matters

Running inference locally is increasingly a security and data-control decision, not just a hobbyist one:

  • Nothing leaves the network. Prompts, documents and outputs never touch a vendor's servers: no logging, no training on your data, no third-party retention.
  • Full control of the stack. You choose the model, the system prompt and the policy, and you can inspect every layer rather than trusting a hosted black box.
  • Air-gap-friendly. The same setup runs with no internet at all, which matters for sensitive analysis work.

Part 1 — A Dense 24B Model, Fully on One GPU

The first model runs on llama.cpp's server, built from source with the CUDA backend. The launch script is the whole config in one place:

#!/bin/bash
cd ~/llama.cpp/build/bin || exit

./llama-server \
  -m ~/models/Dolphin-Mistral-24B-Venice-Edition.Q6_K.gguf \
  -ngl 999 \
  --ctx-size 32768 \
  --batch-size 512 \
  --ubatch-size 64 \
  --cache-type-k q8_0 \
  --cache-type-v q8_0 \
  --host 0.0.0.0 \
  --port 8080

Each flag is a deliberate choice to fit a large model on one GPU while keeping it usable:

SettingChoice
Enginellama.cpp llama-server, compiled from source (CUDA)
ModelDolphin-Mistral-24B (Venice Edition), an uncensored fine-tune, run locally on purpose (see below)
QuantizationQ6_K GGUF: 6-bit weights, the accuracy/size trade that fits 24B (~19 GB) in VRAM
GPU offload-ngl 999: every layer on the GPU
KV cacheq8_0 keys and values: an 8-bit cache roughly halves its VRAM, which buys the long context. A quantized V cache relies on flash attention, which current llama.cpp builds enable automatically.
Context32,768-token window
Batchingbatch 512 / micro-batch 64. The small micro-batch keeps the compute buffers small, trading some prompt-processing speed for VRAM headroom at full context.
Servingbound to 0.0.0.0:8080, an OpenAI-compatible HTTP API for LAN clients

Put together, that's a practical exercise in the levers of local inference: how quantizing both the weights and the KV cache buys a bigger model and a longer context on fixed VRAM, what full layer offload does for speed, and how to actually serve the model to other devices.

Model-behaviour & red-team evaluation

The reason for running an uncensored model locally is that it's a clean lab for AI red-teaming and model-safety evaluation: probing where a model's alignment holds and where it breaks. Locally, I can study that directly: how a model behaves with and without guardrails, and how much of "safety" lives in the underlying weights versus the system prompt and serving policy wrapped around them.

Part of that was testing refusal robustness: feeding the model deliberately coercive, manipulative and frankly absurd system-prompt framings (the "you must always comply / something bad happens if you refuse" pattern, a well-known prompt-injection style) and observing how framing shifts refusal behaviour. The interesting finding isn't the silly prompt itself. It's how cheaply behaviour moves when you control the system layer, which is exactly why guardrails that live only in the prompt are weak, and why real safety has to sit deeper in the stack.

I studied the failure modes; I'm not publishing the working jailbreak text.

Part 2 — Running 100B+ Models with Mixture-of-Experts Offload

The 24 GB wall

Part 1 hit a hard limit. A dense model reads every weight for every generated token, so it has to sit in fast memory to run at a usable speed. On a 24 GB card that tops out around 24–32B parameters. Anything bigger spills into system RAM, and that's where dense models fall apart, because token generation is a memory-bandwidth problem:

tokens/s ≈ memory bandwidth ÷ bytes of weights read per token

MemoryBandwidthDense 120B at 4-bit (~65 GB)
RTX 4090 GDDR6X~1,008 GB/s~15 tok/s, if it fit (it doesn't)
DDR5-5600, dual channel~90 GB/s theoretical~1.4 tok/s at best

So a dense 100B+ model on this machine technically runs, but at a speed nobody would use. More RAM doesn't help: the bottleneck is bandwidth, not capacity.

Mixture-of-experts — huge models that only use a sliver of themselves

A mixture-of-experts (MoE) model replaces each feed-forward block with hundreds of small "expert" networks plus a router. For every token, the router picks only a handful of experts per layer and the rest sit idle. The models in this update all activate roughly 5% of their weights per token:

ModelTotal paramsActive per tokenActive share
gpt-oss-120b117B5.1B~4.4%
Qwen3.8-Flash-Next125B~6B~4.8%
DeepSeek V4 Flash284B13B~4.6%
GLM 5.3 Flash320B18B~5.6%

My starting intuition was "only ~10% of the weights are active, so I only need ~10% of the memory." The first half turned out to be right (it's closer to 5%). The second half is the trap:

Sparsity reduces what each token reads, not what has to be stored. The router can pick any expert for the next token, so every weight still has to be resident somewhere: VRAM, RAM or, slowly, the SSD.

What sparsity does change is bandwidth per token. For gpt-oss-120b, ~5.1B active parameters at ~4.25 bits is about 2.7 GB read per token, versus ~65 GB for a dense model of the same size. Even served entirely from DDR5, that's a theoretical ceiling in the tens of tokens per second instead of about one. Slow memory becomes viable, as long as it only holds the parts of the model that are used sparsely.

Memory budget

TierCapacityRole
VRAM24 GBEverything used on every token (attention, router, shared tensors, KV cache), then as many experts as still fit
System RAM96 GBThe remaining experts, computed on the CPU, plus the OS (~8 GB kept free)
NVMe—Model files, memory-mapped. A fallback tier: if weights have to be read from here, speed collapses.
Usable for weights~110 GBVRAM + RAM minus OS headroom

That ~110 GB is the real ceiling. The ~120B-class models fit comfortably at 3–4 bits. The 284–320B models only fit at roughly 2–3 bits per weight: DeepSeek V4 Flash's build is a 91 GB file, and GLM 5.3 Flash's builds range from 79 to 114 GB. So the honest claim isn't "any model size": it's models whose weights are up to about four times the GPU's memory, at interactive speed.

Serving architecture

LayerToolRole
Engine 1llama.cpp llama-serverGeneral-purpose. Runs any GGUF, dense or MoE, with manual control over which tensors go to the GPU and which to RAM.
Engine 2PolyStrataPurpose-built for very large MoE models. Places individual experts across VRAM, RAM and SSD by how often they're used.
ClientPiTerminal coding agent on my workstation, talking to whichever engine is up over the LAN.

Only one engine runs at a time, on the same port and with the same API key. That's not a limitation I worked around; it's a consequence of the memory budget. Each of these models wants most of the 96 GB, so two can't be resident together. Because both engines speak the same OpenAI-compatible API, the client never needs to know which one is serving.

Engine 1 — llama.cpp hybrid offload (gpt-oss-120b)

Not every tensor in an MoE model is sparse. Attention, embeddings, normalization and the router run on every token; only the routed experts are sparse. That gives a natural split:

ComponentAccess patternPlacement
Attention, shared tensors, routerDense, every tokenGPU: needs GDDR6X bandwidth
KV cacheEvery token, grows with contextGPU
Routed experts (most of the file)Sparse, 4 of 128 per layerRAM, computed on the CPU
Leftover VRAM—Filled with as many expert layers as fit
 
#!/bin/bash
cd ~/llama.cpp/build/bin || exit

./llama-server \
  -m ~/models/gpt-oss-120b-mxfp4.gguf \
  -ngl 999 \
  --n-cpu-moe 28 \
  -fa on \
  --ctx-size 32768 \
  --batch-size 2048 \
  --ubatch-size 2048 \
  --threads 16 \
  --host 0.0.0.0 \
  --port 8080 \
  --api-key-file ~/.config/llm/api-key
FlagWhat it does
-ngl 999Puts every layer on the GPU by default, so attention and shared tensors land in VRAM…
--n-cpu-moe N…then overrides that for expert weights only, keeping the experts of the first N layers in system RAM. This is the key flag.
-fa onFlash attention: smaller attention buffers, so more VRAM is left for experts.
--ubatch-size 2048The opposite choice from Part 1. With experts in RAM, large micro-batches let llama.cpp stream expert weights to the GPU once per chunk, which speeds up prompt processing considerably.
--threads 16One per physical core of the 9950X3D. The CPU computes the RAM-resident experts during generation, so thread count directly affects speed.
--api-key-fileAuthentication on the LAN endpoint, with the key read from a file rather than passed on the command line, where ps would show it to every local user.

gpt-oss-120b ships with its expert weights natively in MXFP4 (4-bit microscaling floating point), so there's no third-party quantization and no accuracy lost to one. The whole model is ~63 GB, which leaves comfortable headroom in 96 GB of RAM.

The only number that really needs tuning is how many expert layers live in RAM:

  1. Start with --n-cpu-moe 36, the model's full layer count, so every expert is in RAM. It's guaranteed to load.
  2. Lower it step by step, moving one more expert layer onto the GPU each time, benchmarking each step with llama-bench.
  3. Stop when VRAM is within ~1–2 GB of full with the full 32k context allocated. Measuring with an empty context gives a misleading result that runs out of memory later in a long session.

An equivalent, finer-grained way to make the same split is to pin tensors with a regex: -ot ".ffn_.*_exps.=CPU". --n-cpu-moe is the simpler interface; -ot gives per-tensor control.

Engine 2 — PolyStrata, frequency-aware expert caching

llama.cpp splits at the level of whole layers: "the experts of layers 0–N go to RAM." PolyStrata (an open-source project built on Niko1221's Strata engine) works at the level of individual experts, based on how often each one is actually used. Expert usage isn't uniform, so if the hot experts sit in the fastest tier, most of each token's work hits GDDR6X even though the model is several times larger than the card. It's a cache hierarchy applied to model weights.

PolyStrata runs these three models through two engines and can switch between them while the server is running:

ModelExpert layoutBuildOn diskEngine
Qwen3.8-Flash-Next24,576 experts, 10 per tokenIQ3_S (installer default at 96 GB RAM)~52 GiBStrata's original engine
DeepSeek V4 Flash11,008 experts: 256 in each of 43 layers, 6 + 1 shared per layerUD-IQ2_XXS (the only size)91 GBstrata-poly (experimental)
GLM 5.3 Flash12,096 experts: 288 in each of 42 layers, 8 per layerreduced build (UD-IQ2_XXS)~80–100 GBstrata-poly (experimental)
TierWhat lives there
VRAMAttention, KV cache and the most frequently used experts. The engine counts which experts your workload actually uses and re-chooses at the next start.
RAMThe remaining experts, computed by the CPU in parallel with the GPU.
NVMeThe model files, used in place (memory-mapped, no second copy). For Qwen, also a large lookup table.

Three more techniques stack on top:

  • Speculative decoding. A small draft model (or a draft block built into the model) guesses the next few tokens, and the big model verifies them in a single pass. Verifying several tokens costs about the same as generating one, so every correct guess is nearly free. The published speedups are 1.6–1.8× for Qwen and 1.1–1.2× for GLM; DeepSeek doesn't use it yet.
  • Chunked prefill. Long prompts are processed in large chunks (up to 8,192 tokens for Qwen, 1,024 for GLM and DeepSeek), with experts that aren't on the GPU streamed through it once per chunk. This addresses the prompt-processing weak spot of CPU-resident experts.
  • Compressed attention memory (DeepSeek). DeepSeek V4 Flash reads only the last 128 tokens in full and the rest as compressed rows, about 6.9 KB per token of context. A long context therefore leaves almost all of the VRAM free for experts.

The GLM and DeepSeek engine is explicitly experimental and Linux-only, and its developers have validated it on 32 GB cards. On a 24 GB card, fewer experts fit in VRAM and more of the work falls to the CPU, so I treat those two as stretch models and Qwen3.8-Flash-Next as the daily driver.

For LAN access, PolyStrata needs an explicit host setting and an API key, set at install time:

./setup.sh --setup --host 0.0.0.0 --api-key "$LLM_API_KEY"
Use caseEngineWhy
Qwen3.8-Flash-Next, GLM 5.3 Flash, DeepSeek V4 FlashPolyStrataExpert-level caching and speculative decoding beat a layer-level split for these models
gpt-oss-120b, the dense Dolphin 24B, any new GGUFllama.cppRuns anything, full control over every flag, and what I know how to tune and debug

Client — Pi as a terminal coding agent

The server runs headless. I work from my workstation through Pi, an open-source, minimal terminal coding agent. It ships with four tools (read, write, edit, bash) and leaves the rest to extensions and configuration, which suits this project: it's a thin, inspectable layer, not a black box wrapped around the model.

npm install -g @earendil-works/pi-coding-agent

Custom endpoints go in ~/.pi/agent/models.json. Since only one engine runs at a time on the same address, a single provider covers all of them:

{
  "providers": {
    "homelab": {
      "baseUrl": "http://<server-lan-ip>:8080/v1",
      "api": "openai-completions",
      "apiKey": "<LLM_API_KEY>",
      "models": [
        { "id": "qwen3.8-flash-next" },
        { "id": "deepseek-v4-flash" },
        { "id": "glm-5.3-flash" },
        { "id": "gpt-oss-120b" },
        { "id": "dolphin-mistral-24b" }
      ]
    }
  }
}

The model ID is effectively a label: the engine that's running decides what actually answers. The full loop is Pi on the workstation → LAN → llama-server or PolyStrata on the 4090 box → back. No prompt, file or line of code leaves the network at any point, which extends Part 1's guarantee from chat to a real agentic coding workflow.

Agent security — a new attack surface

Giving a model a shell changes the threat model. A chat model can only produce text; Pi can read and edit files and run bash commands. That means:

  • Prompt injection becomes command execution. A malicious instruction hidden in a README, a dependency or a code comment that the agent reads could turn into a shell command. This connects directly to the red-team work: Part 1 showed how cheaply the system layer moves model behaviour, and here the consequence is an action, not just text.
  • An uncensored model with tool access removes one more layer of defence, so when I pair one with Pi, I treat it as untrusted code execution.

When Pi runs on the server itself, which is how I use it day to day, it doesn't ask before running a command, so the control is a sandbox rather than review. A small launcher runs it under bubblewrap:

  • Fresh namespaces for everything (--unshare-all). The system is mounted read-only and my home directory is replaced by an empty one, so SSH keys, tokens and browser data aren't even visible.
  • Only the current project folder is writable, and the launcher refuses to start from my home directory or /.
  • The environment is cleared and there's no network: the only way out is a Unix socket bridged to the model's port. Checked from inside: loopback only, no DNS.

Trade-offs and limits

  • Prompt processing is the weak spot. Generation touches a few experts per token, but a long prompt touches nearly all of them. Large micro-batches and chunked prefill soften this but don't remove it, so long-document work feels it more than chat does.
  • Memory capacity is still a hard limit. Sparsity doesn't let a 200 GB model run in 120 GB at usable speed; it only makes slow memory fast enough to be useful. The 284–320B models fit only because they're quantized to about 2–3 bits, which costs some quality.
  • RAM speed matters more than GPU speed here. Faster DDR5 or more memory channels would raise generation speed more than a faster GPU would.

Security changes made in this update

Reviewing the Part 1 config showed the endpoint was bound to 0.0.0.0 with no authentication: anything on the LAN could query the model, including a compromised IoT device. For a project whose whole point is data control, that was a real gap.

  • Both engines now require an API key, read from a file only my user can read (--api-key-file for llama.cpp; PolyStrata gets it through an environment variable set from that file), so it never appears on a command line, where ps would show it to every local user.
  • Part 3 took the fix further: the engines now listen on loopback only, the LAN firewall rule for port 8080 is gone, and the only way in is through an authenticated reverse proxy (see below).

Extending the red-team work

The update adds a useful comparison point. Part 1 used an uncensored fine-tune, which shows behaviour with most of the safety training removed. gpt-oss-120b is a safety-trained model, so the same evaluation now has a control. The next round of tests runs the same set of coercive and manipulative system-prompt framings against both models and measures refusal rates under a neutral prompt versus the coercive ones.

That shifts the question from "can the prompt layer move behaviour?" to "how much more resistant are safety-trained weights than prompt-level guardrails, and where does that resistance break?" As before, I'll publish the method and aggregate results, not the working prompts.

What the update adds

Part 1 was about fitting a model to the hardware. Part 2 is about fitting the hardware to the model's architecture: understanding which tensors are dense and which are sparse, placing each in the memory tier that matches its access pattern, and reasoning about speed from first principles (bandwidth ÷ bytes per token) rather than by trial and error. The result is models with up to 13× the parameters of Part 1's, and weights about four times larger than the GPU, running privately at interactive speed, driven by an agentic coding client, with the same "nothing leaves the network" guarantee as the original setup.

Part 3 — Remote Access: Open WebUI Through a Tunnel, With No Open Ports

The goal

Parts 1 and 2 only worked on my own network. I wanted the lab from anywhere: a browser chat interface on my phone, and the same OpenAI-compatible API for Pi on a laptop. Three constraints:

  • No open ports at home. Nothing forwarded on my router, and my home IP never published.
  • The relay doesn't get to read anything. Something with a public address has to sit in the middle, but it should only ever see ciphertext.
  • The engines stay unexposed. They listen on the machine they run on and nowhere else.

The off-the-shelf answer, Cloudflare Tunnel, fails the second constraint: it terminates TLS at Cloudflare's edge, so a third party would see every prompt. That defeats the point of this project, so I built the path myself.

Architecture

HopComponentWhat it does
Internet → VPSnginx stream (layer 4)Accepts HTTPS on 443 and forwards the raw TLS bytes without decrypting them. Adds a PROXY protocol header with the client's real address. If the PC is unreachable, falls back to a static offline page.
VPS → homeWireGuardThe PC dials out to the VPS and keeps the tunnel open (keepalive every 25 s), so nothing at home listens on the internet. Split tunnel: only the 10.8.0.0/24 tunnel subnet goes through it.
Home PCCaddyListens only on the tunnel address. TLS ends here, with a Let's Encrypt certificate obtained through the passthrough (TLS-ALPN-01), so the certificate's private key never leaves the PC.
RoutingCaddy/v1/* requires the API key as a bearer token (401 otherwise) and goes to the engine on 127.0.0.1:8080. Everything else goes to Open WebUI.
Front endOpen WebUIRuns in Docker on 127.0.0.1:3000 and talks to the engine over loopback with the same key.

The VPS side is a few lines of nginx:

stream {
    upstream pc_https {
        server 10.8.0.2:443 max_fails=1 fail_timeout=10s;   # the PC, over WireGuard
        server 127.0.0.1:8443 backup;                       # offline page
    }
    server {
        listen 443;
        proxy_pass pc_https;
        proxy_protocol on;
        proxy_connect_timeout 3s;
    }
}

The PC side is the whole Caddyfile. A setup script writes the key in, and the file is readable only by root and the caddy user:

{
    admin off
    auto_https disable_redirects
    servers {
        listener_wrappers {
            proxy_protocol {
                allow 10.8.0.1/32
            }
            tls
        }
    }
}

llm.example.dev {
    bind 10.8.0.2
    tls {
        issuer acme {
            disable_http_challenge
        }
    }
    log {
        output file /var/log/caddy/access.log
        format json
    }

    @unauthorized {
        path /v1/*
        not header Authorization "Bearer <API_KEY>"
    }
    handle @unauthorized {
        respond 401
    }
    handle /v1/* {
        reverse_proxy 127.0.0.1:8080
    }
    handle {
        reverse_proxy 127.0.0.1:3000
    }
}

Locking down the PC

One finding from the Open WebUI setup: settings like ENABLE_SIGNUP are read from the environment only on first start and then stored in its database, which wins from then on. My "signups disabled" flag was silently ignored, and I only found out because a test registration went through. Disabling signups in the admin panel fixed it. The lesson: test the control, don't trust the flag.

Real client addresses: PROXY protocol

Passthrough has a side effect. Every connection Caddy sees comes from the VPS's tunnel address, so every line in the access log said 10.8.0.1. That's useless for auditing and fatal for banning: banning that address would ban everyone, tunnel included.

The fix is the PROXY protocol. nginx prepends one plain-text line with the original client address to each connection, and Caddy's proxy_protocol listener reads it, but only from 10.8.0.1, so nobody else can claim an address. Two details matter:

  • Order. The header arrives before the TLS handshake, so the PROXY listener has to sit in front of the tls one.
  • Both sides switch together. If Caddy doesn't expect the header, it reads PROXY TCP4 … where a TLS ClientHello should be and drops the connection.

Brute-force protection, split across two machines

What's exposed now is the Open WebUI login and the API. A standard fail2ban setup doesn't fit this topology, because no single machine has both halves of the picture:

MachineCan seeCan't see
VPSThe real source address of every packet, and it can drop them before they reach anythingWhich requests failed: the traffic is encrypted end to end
PCDecrypted requests, status codes, failed loginsA useful source address at the packet level: everything arrives from the tunnel

So detection runs on the PC and enforcement on the VPS:

  1. Detect. fail2ban on the PC reads Caddy's JSON log for failed logins (POST /api/v1/auths/signin answered with a 4xx) and for /v1 requests rejected for a bad key. Ten failures in ten minutes earn a one-hour ban.
  2. Push. The ban action connects to the VPS over SSH, through the tunnel, as a dedicated account whose key can do exactly one thing.
  3. Validate. On the VPS, that one thing is a script that accepts only ban <ipv4> <seconds> or unban <ipv4>, checks every field before touching the firewall, and rejects anything else. I tested it with injection strings like 1.2.3.4;id and $(id).
  4. Enforce. Bans go into an nftables set with a timeout on each entry, dropping only TCP 80 and 443.
# /var/lib/f2bpush/.ssh/authorized_keys on the VPS
from="10.8.0.2",restrict,command="sudo -n /usr/local/sbin/f2b-nft" ssh-ed25519 AAAA… f2b-push

# the ban set, created on first use
table inet f2b {
    set banned { type ipv4_addr; flags timeout; }
    chain input {
        type filter hook input priority -10; policy accept;
        tcp dport { 80, 443 } ip saddr @banned drop
    }
}

The key only works from the tunnel address, restrict removes shells, terminals and forwarding, and the forced command runs no matter what the client asks for. sudo allows that one script and nothing else, with no arguments. The narrow drop rule is deliberate: if I lock myself out from home, the ban can't also cut WireGuard or SSH from the same address, and every ban expires on its own even if the unban never arrives.

The filter matches the client address Caddy took from the PROXY header, not X-Forwarded-For or anything else a client controls. Caddy also escapes quotes inside logged header values, so text smuggled into a header, like a fake client address or status, can't form a match. Nobody can get someone else banned that way; I tested it with forged fields.

Debugging: status 000 and an empty log

The first end-to-end test after switching on the PROXY protocol failed at the TLS layer (curl status 000), and Caddy logged nothing at all. Working through it one layer at a time:

  • Test with the right name. Curling the tunnel IP directly sends no SNI and fails for its own reasons. curl --resolve llm.example.dev:443:10.8.0.2 sends the real hostname to a chosen address.
  • Take nginx out of the loop. curl --haproxy-protocol sends the same header nginx does, straight to Caddy.
  • Two separate faults turned up. Caddy couldn't write to its log directory and refused to start; letting systemd own the directory (LogsDirectory=) creates it with the right owner. And with debug logging on, Caddy finally said "first record does not look like a TLS handshake": the PROXY header was reaching the TLS parser, because the Caddyfile on disk was still the version without the PROXY listener. The updated one had been written but never deployed.

The lesson I'm keeping: check the configuration that's actually loaded (caddy adapt shows whether the listener is there), not the file you believe you deployed.

Incident: two leaked secrets, rotated

Two secrets were exposed during the build: the VPS's WireGuard private key, while I was copying configuration between machines, and the API key, which Caddy's debug output printed in full, because its config dump includes the header matcher, bearer token and all. Both were rotated the same day:

  • API key. The first step was finding every copy. The engines read the key from a file at start, so a restart was enough, and the Caddyfile was regenerated. Open WebUI was the surprise: like the signup setting, it keeps its own copy in its database and ignores the environment after first start, so the new key had to go in through its admin panel.
  • WireGuard. A new keypair on the VPS, applied live without the private key ever appearing on screen or on a command line, then the PC's peer entry updated. The tunnel was down for a few minutes, and the offline page covered it.

Takeaways: debug logging is a disclosure channel, and before rotating a secret you need a complete list of where it lives, including copies an application quietly keeps for itself.

Does this break "nothing leaves the network"?

Partly, so it's worth being precise. In remote use, prompts do cross the internet and a rented server, but only as TLS ciphertext that's decrypted on my PC; the VPS just forwards it. The engines themselves still have no internet access: they bind loopback, and PolyStrata runs with its downloads and outbound features switched off. And the original mode is one command away: stop the tunnel, and the lab is offline again.

Limits

  • The VPS is still trusted for identity. DNS points at it, so whoever controls it could get a certificate for the hostname and sit in the middle; it even holds one already, for the offline page. Passthrough protects against a curious provider and against logs, not against a compromised VPS. A CAA record pinned to the PC's ACME account would narrow that, at the cost of the offline page's own certificate.
  • The login page is on the internet. fail2ban slows guessing from one address; it doesn't stop an attacker with many. Strong, unique passwords carry the weight, and the stronger next step is to make the web UI reachable only through a client VPN.
  • The hostname went public with the certificate. Certificate Transparency logs publish every hostname a public CA issues, and scanners watch them. Authentication has to be in place before the first certificate, not after.
  • Bans live in memory on the VPS. A VPS reboot clears them, and the PC doesn't know. For one-hour bans that's acceptable.
  • IPv4 only, matching what nginx listens on.

What the update adds

Parts 1 and 2 were about making big models run. Part 3 is about exposing a service without exposing the machine: no inbound ports at home, TLS the relay can't read, least privilege at every step (loopback binds, a key that can run one script, sudo for one command), detection and enforcement each placed where they can actually work, and the unglamorous part: testing the controls, reading the logs, and rotating secrets when they leak.

How it maps to security work

This sits at the intersection of four current security specializations. Self-hosting and ML-ops: running large models efficiently and privately on your own infrastructure, down to which tensor lives in which memory tier. AI red-teaming: understanding alignment failure modes, prompt injection, and where model guardrails actually live. Agent security: what changes when a model can act, not just answer. And secure service exposure: publishing a private service through an untrusted relay with no open ports, least-privilege automation, and incident response when secrets leak. This project is hands-on grounding in all four.
